# 志望理由ES設計の教科書  
## 自分の価値観・企業理解・コース理解を接続するための再現可能な型

---

## 0. この教科書の目的

この資料は、インターンシップや本選考の志望理由ESを、毎回その場の勢いで書くのではなく、再現性のある構造で設計するためのものです。

目標は、単に「きれいな文章」を書くことではありません。  
採用側に次の3点を伝えることです。

1. **自分は何を実現したい人なのか**
2. **なぜその企業・コースでなければならないのか**
3. **そこで何を学び、どのように貢献できるのか**

志望理由ESは、企業を褒める文章ではありません。  
自分の価値観と企業・コースの仕事の性質が交差する地点を示す文章です。

---

# 第1章　志望理由ESの基本思想

## 1-1. 志望理由ESの役割

志望理由ESの役割は、以下の問いに答えることです。

> **この人は、なぜこの企業・このコースで学ぶ必然性があるのか。**

そのためには、次の3つを接続する必要があります。

| 要素 | 内容 |
|---|---|
| 自分 | 価値観、原体験、強み、現在の不足 |
| 企業 | 仕事の性質、担う責任、発生する判断 |
| コース | 扱う対象、工程、制約、得られる経験 |

よくある弱いESは、この3つが分離しています。

> 私はこういう経験をしました。  
> 貴社はこういう会社です。  
> だから志望します。

この形だと、自分語りと企業説明が接続されません。

強いESはこうです。

> 自分が過去に見た課題構造と、企業・コースが扱う課題構造が同型である。  
> だから、その環境で学ぶ必然性がある。  
> さらに、自分の経験を活かして貢献できる。

---

## 1-2. あなたのESの核

あなたの志望理由全体の母体になる価値観は、次の一文です。

> **人の努力や判断が個人に閉じて消費される状態を、基準・役割・情報・技術によって、組織全体で再現できる仕組みに変えたい。**

この核は、企業や職種によって以下のように変換できます。

| 対象 | 変換後の表現 |
|---|---|
| SIer | 顧客業務の曖昧な判断を、要件・設計・運用に落とし込む |
| DX | 業務や情報の流れを再設計し、使われ続ける仕組みにする |
| 生成AI | AIが参照する情報、人が確認する条件、出力を使う基準を設計する |
| データサイエンス | データ・評価指標・検証条件を通じて、判断材料を作る |
| 公共・基盤 | 止められない仕組みの中で、品質・責任・影響範囲を踏まえて技術を導入する |
| R&D | 技術を実用条件下で成立させるため、精度・速度・限界を検証する |

重要なのは、核を変えることではありません。  
**核を、応募先の仕事の言葉に翻訳すること**です。

# 第2章　志望理由ESの全体構造

## 2-1. 基本構造

志望理由ESは、次の6段階で設計します。

```text
① 志望理由・実現したい状態
② 原体験・原体験からの問題意識
③ 現在との差分・自分に足りない実務条件
④ Why御社
⑤ Whyそのコース
⑥ どのようなことを学び、どう貢献するか
```

それぞれの役割は以下です。

| 段階 | 役割 |
|---|---|
| ① 実現したい状態 | 冒頭で自分が作りたい価値を示す |
| ② 原体験 | なぜその価値観を持ったかを示す |
| ③ 現在との差分 | なぜインターンで学ぶ必要があるかを示す |
| ④ Why御社 | なぜその企業なのかを示す |
| ⑤ Whyそのコース | なぜそのコース・テーマなのかを示す |
| ⑥ 学び・貢献 | 参加後に得たい判断軸と持ち込める強みを示す |

---

## 2-2. 文章全体の基本テンプレート

最大構造は以下です。

```text
私は、【実現したい状態】を目指したい。

【原体験】では、【表面的な問題】が起きていたが、私はその原因を【構造的原因】にあると捉えた。
この経験から、【価値観・問題意識】を持った。

一方で、現在の私は【経験済みのこと】には取り組んできたが、
【実務特有の制約】を踏まえて【必要な判断】を行う経験はまだない。

貴社は【仕事の性質】を通じて、【担う責任】を担っており、
そこでは【企業で発生する判断】が重要になると考える。

本コースでは、【対象・工程】を通じて、【コースで発生する判断】を実践できる点に惹かれた。

私の【持ち込める強み】を活かし、
【学びたい判断軸】を身につけるとともに、【貢献】につなげたい。
```

これはあくまで最大構造です。  
400字では圧縮し、500字では一部を展開します。

# 第3章　各段階の因数分解

---

## 3-1. ① 志望理由・実現したい状態

### 定義

冒頭では、企業を褒めるのではなく、**自分が実現したい状態**を置きます。

### 因数分解

```text
実現したい状態
＝ 自分の価値観
× 企業・職種が扱う課題構造
× 技術によって作りたい変化
```

### 各要素の意味

| 要素 | 内容 |
|---|---|
| 自分の価値観 | 何を問題だと感じ、どんな状態に変えたいのか |
| 課題構造 | 企業・職種の現場にも存在する構造的な問題 |
| 技術による変化 | IT・AI・データ・システムによって作りたい状態 |

### 書き方テンプレート

```text
私は、【対象業務・領域】において、
【属人化・曖昧さ・判断のばらつき】を、
【IT・AI・データ・システム】によって
【再現可能な状態】へ変える考え方を学びたい。
```

### 例：SIer向け

```text
私は、顧客業務に閉じた判断や工夫を、ITによって関係者が共有し、再現できる仕組みに変える考え方を学びたい。
```

### 例：生成AI向け

```text
私は、生成AIを個人の作業補助にとどめず、業務の中で何を参照し、どこを人が確認するかまで設計された仕組みに落とし込む考え方を学びたい。
```

### 例：公共基盤向け

```text
私は、先端技術を便利な実証で終わらせず、社会基盤の中で安心して使い続けられる仕組みに落とし込む判断を学びたい。
```

### NG例

```text
貴社の先端技術を活用した社会課題解決に魅力を感じました。
```

### なぜ弱いか

- 誰でも言える
- 企業を褒めているだけ
- 自分が実現したい状態が見えない
- 仕事で発生する判断が見えない

## 3-2. ② 原体験・原体験からの問題意識

### 定義

原体験は、過去の詳細説明ではありません。  
志望理由で使う原体験は、**価値観が生まれた根拠**です。

### 因数分解

```text
原体験からの問題意識
＝ 出来事
× 違和感
× 原因構造
× 得た価値観
```

### 各要素の意味

| 要素 | 内容 |
|---|---|
| 出来事 | 大学祭、研究、教材作成など |
| 違和感 | 何に違和感を持ったか |
| 原因構造 | 表面的な問題の奥にある構造 |
| 得た価値観 | その経験から何を大切にするようになったか |

### 書き方テンプレート

```text
【原体験】では、【表面的な問題】が起きていた。
私はその原因を、【人の努力不足ではなく、構造的な原因】にあると捉えた。
この経験から、【自分の価値観】に関心を持った。
```

---

### 素材別の使い方

#### 1. 大学祭を使う場合

大学祭の本質は、イベント運営ではありません。  
本質は、**基準と役割を整え、経験差があっても迷わず動ける仕組みを作った経験**です。

```text
大学祭では、返却作業の遅れを団体や局員の努力不足ではなく、片付け基準と受付後の役割分担の曖昧さにあると捉えた。
この経験から、人の努力を成果につなげるには、基準や役割を整え、迷わず動ける仕組みにする必要があると学んだ。
```

#### 2. 研究を使う場合

研究の本質は、技術名ではありません。  
本質は、**AIの出力を評価指標・検証条件・入力設計まで含めて扱った経験**です。

```text
研究では、深層学習モデルの精度が伸びない原因を、モデル単体ではなく、入力形式や評価方法まで戻って捉え直した。
この経験から、技術は動かすだけでなく、何を基準に使えると判断するかまで設計する必要があると学んだ。
```

#### 3. 教材作成を使う場合

教材作成の本質は、資料作成ではありません。  
本質は、**知識を残すだけでなく、使う人が動ける形に並べ直した経験**です。

```text
研究室で教材を作成した際、資料が残っていても、初学者が何をどう使えばよいか分からなければ行動にはつながらないと感じた。
この経験から、知識は残すだけでなく、使う人の迷いに沿って並べ直す必要があると学んだ。
```

## 3-3. ③ 現在との差分・自分に足りない実務条件

### 定義

現在との差分とは、**ここまでは経験したが、実務ではまだ経験していない条件**を示す部分です。

志望理由の説得力は、憧れよりも不足の自覚で出ます。

### 因数分解

```text
現在との差分
＝ これまで経験したこと
× まだ経験していない実務条件
× その差分がなぜ重要か
```

### 各要素の意味

| 要素 | 内容 |
|---|---|
| これまで経験したこと | 学生組織、研究、個人開発などで経験済みのこと |
| 実務条件 | 顧客、既存システム、品質責任、セキュリティ、運用など |
| 差分の重要性 | なぜその実務条件を学ぶ必要があるのか |

### 書き方テンプレート

```text
一方で、私は【これまで経験したこと】には取り組んできたが、
【実務特有の制約】を踏まえて【企業・職種で必要な判断】を行う経験はまだない。
```

### 例：SIer向け

```text
一方で、学生組織では人の動き方を整える経験にとどまり、実際の顧客業務や既存システムの制約を踏まえて、ITで仕組み化する経験はまだない。
```

### 例：生成AI向け

```text
一方で、個人でAIを活用する経験はあるものの、チームの開発工程の中で、AIの出力をどの条件で採用し、人がどこを確認すべきかを設計する経験はまだない。
```

### 例：R&D向け

```text
一方で、研究では制御された条件での検証が中心であり、実社会の不完全なデータや運用制約の中で、技術をどの水準なら使えるか判断する経験はまだない。
```

## 3-4. ④ Why御社

### 定義

Why御社は、企業の特徴を列挙する部分ではありません。  
**自分の価値観と、その企業の仕事の性質が交差する理由**を示す部分です。

### 完成式

```text
Why御社
＝ 自分の価値観
× 企業の仕事の性質
× その企業が担う責任
× その企業で発生する判断
× 自分が持ち込める強み
```

---

### 4-1. 自分の価値観

あなたの場合、基本の価値観は次です。

```text
人の努力や判断が個人に閉じて消費される状態を、仕組みで支えたい。
```

企業・職種ごとに変換します。

| 対象 | 変換 |
|---|---|
| SIer | 顧客業務に閉じた判断や工夫を、ITで再現可能な仕組みに変えたい |
| 生成AI | 人に閉じた知識や判断を、AIが参照でき、人が確認できる形に変えたい |
| 公共基盤 | 多くの人が当たり前に使う仕組みを、裏側の設計と運用で支えたい |
| R&D | 技術を研究内の成果で終わらせず、実用条件で使える形に近づけたい |

---

### 4-2. 企業の仕事の性質

企業研究では、事業名を拾うだけでは弱いです。  
次のように変換します。

```text
何をやっている会社か
↓
どんな立場で、どんな責任を、どこまで担っている会社か
```

### 弱い例

```text
貴社は官公庁、金融、医療など幅広い領域に関わっている。
```

### 強い例

```text
貴社は、公共性の高い大規模システムを、顧客業務の理解から構築・運用まで長期に担っている。
```

### さらに強い例

```text
貴社は、止められない社会基盤に対して、顧客業務・既存システム・運用制約を踏まえながら、技術を実装し続けている。
```

---

### 4-3. その企業が担う責任

「企業らしさ」は、事業領域よりも **担う責任** に出ます。

| 企業・領域の例 | 担う責任の例 |
|---|---|
| 大規模SIer | 社会基盤を止めずに支え、更新し続ける責任 |
| AI・データ社会実装 | AIを安全・安心に、信頼して使える形にする責任 |
| 社会インフラ・OT/IT | 現場設備・業務・ITを結び、実運用まで成立させる責任 |
| 保守運用・BPO | 導入後も顧客業務に長く伴走し、変化に対応する責任 |
| 技術商社・マルチベンダー | 技術選択肢を比較し、顧客課題に合う形で実装につなげる責任 |

---

### 4-4. その企業で発生する判断

Why御社の強さは、ほぼここで決まります。

企業の特徴を挙げるだけではなく、**その企業の仕事で発生する判断**まで書きます。

| 企業・領域 | 発生する判断 |
|---|---|
| 大規模SIer | 既存業務や運用を止めずに、どの範囲から技術を導入し、どの品質なら運用に乗せるか |
| AI・データ社会実装 | AIの便利さだけでなく、誤出力や説明責任を踏まえ、どの条件なら顧客業務で信頼して使えるか |
| 社会インフラ・OT/IT | 現場設備・業務・ITシステムの制約を踏まえ、どこを標準化し、どこを現場に合わせるか |
| 保守運用・BPO | 導入時の最適化だけでなく、保守運用で変化する業務にどう継続対応するか |
| 技術検証・マルチベンダー | 多様な技術選択肢の中から、顧客課題・運用・コスト・拡張性を踏まえて何を選ぶか |

---

### 4-5. 自分が持ち込める強み

強みは、直接叫ぶのではなく、企業の判断に接続します。

| 応募先 | 持ち込める強み |
|---|---|
| SIer | 曖昧な現場を、基準・役割・情報の流れに分けて整理する力 |
| 生成AI | AIの出力を、評価条件や人の確認範囲とセットで考える力 |
| DX | 使う人の迷いや業務の詰まりを、仕組みとして設計する力 |
| 基盤 | 多くの人が安心して動くための裏側の基準や運用を整える力 |
| R&D | 技術がうまくいかない原因を、入力・出力・評価まで戻って捉え直す力 |

---

### Why御社のテンプレート

```text
私は【自分の価値観】を大切にしている。
その中で貴社は、【企業の仕事の性質】を通じて、【企業が担う責任】を担っている。
特に、【その企業で発生する判断】が求められる点に惹かれた。
私の【自分の経験・強み】を活かし、【企業で実現したいこと】に取り組みたい。
```

### 実戦用の短縮版

```text
貴社は、【仕事の性質】を通じて、【担う責任】を果たしている。
そこでは、【発生する判断】が重要になると考える。
私は【自分の経験】から【価値観】を持っており、この環境で【学びたいこと・貢献したいこと】に取り組みたい。
```

---

## 3-5. ⑤ Whyそのコース

### 定義

Whyそのコースは、インターンESでは特に重要です。  
会社全体への憧れではなく、**そのコースでしか得られない経験**を示します。

### 因数分解

```text
Whyそのコース
＝ コースで扱う対象
× 体験する工程
× その工程で発生する判断
× コース特有の制約
× 自分に足りない経験
× 自分が持ち込める視点
```

---

### 5-1. コースで扱う対象

まず名詞を拾います。

例：

- 生成AI
- Private AI基盤
- 官公庁
- 通信会社向けシステム
- デジタルツイン
- 中央省庁DX
- 基盤更改
- 設計・構築
- 開発・運用
- プロダクト創造

ただし、名詞を拾うだけでは不十分です。  
名詞はあくまで素材です。

---

### 5-2. 体験する工程

次に、コースで体験できる工程を抜き出します。

| 工程 | 内容 |
|---|---|
| 課題発見 | 顧客や現場の課題を見つける |
| ヒアリング | 関係者の言葉から目的・制約を整理する |
| 要件整理 | 曖昧な要望を実装可能な条件に落とす |
| 設計 | 機能・データ・役割・確認条件を設計する |
| 実装 | 実際に技術を動かす |
| 構築 | 基盤やシステム環境を組み立てる |
| 検証 | 成果物が使える条件を確認する |
| 評価 | 成功条件や品質を測る |
| 運用 | 継続的に使われる状態にする |
| 提案 | 顧客に価値や根拠を説明する |

---

### 5-3. その工程で発生する判断

ここが最重要です。  
コース概要から、仕事上の判断に変換します。

| コース系統 | 発生する判断 |
|---|---|
| 生成AI開発 | AIにどこまで任せるか。生成物をどの観点で人が確認するか。どの水準なら次工程へ進めるか |
| Private AI基盤 | 誰がどの情報をAIに扱わせられるか。権限・ログ・監査・セキュリティをどう設計するか |
| 基盤更改 | 既存運用を止めずに、どの範囲から変更するか。障害時に誰が何を確認するか |
| DXプロダクト | 誰のどの判断を支えるプロダクトにするか。便利さと継続利用の条件をどう両立するか |
| デジタルツイン | 現実をどの粒度でモデル化するか。シミュレーション結果をどこまで信頼し、何の意思決定に使うか |
| データ分析・AIモデル | どのデータを使い、何を評価指標にし、どの条件なら実務で使えると判断するか |

## 3-6. ⑥ どのようなことを学び、どう貢献するか

### 定義

締めでは、「知識を学びたい」ではなく、**判断軸を身につけたい**と書きます。  
さらに、学びだけで終わらせず、持ち込める強みを使ってどう貢献するかまで示します。

### 因数分解

```text
学び・貢献
＝ 学びたい判断軸
× インターン中に取る行動
× 持ち込む強み
× 成果物や議論への貢献
```

---

### 6-1. 学びたい判断軸

弱い表現と強い表現を比較します。

| 弱い表現 | 強い表現 |
|---|---|
| AI活用について学びたい | AIに任せる範囲、人が確認する条件、どの水準なら次工程へ進めるかを判断する軸を身につけたい |
| システム開発について学びたい | 顧客業務の要望を、既存運用や技術制約を踏まえて、どの単位で要件・設計に落とすかを学びたい |
| デジタルツインについて学びたい | 現実空間をどの粒度でモデル化し、シミュレーション結果をどの条件なら意思決定に使えるかを見極めたい |
| DXについて学びたい | 業務・情報・判断の流れを再設計し、利用者が継続して使える状態にする考え方を学びたい |

---

### 6-2. インターン中に取る行動

参加後の姿が見える表現を入れると強くなります。

```text
社員の方から受けたフィードバックをもとに、仮説と評価基準を更新したい。
```

```text
チーム内で目的と評価軸をそろえ、意見の違いを検証すべき仮説として扱いたい。
```

```text

```

| 素材 | 締めへの接続 |

# 第11章　最終原則

## 原則1. 構造はNTTデータ型

```text
学びたいこと
→ 原体験
→ 不足の自覚
→ コースで得られる経験
→ 身につけたい判断軸
```

この構造は再現性が高いです。

---

## 原則2. 深さはNEC型

NEC型の良さは、長い思想ではありません。  
良さは、次のような実務の解像度です。

- 顧客の目的と制約を見る
- AIやITが参照すべき情報を設計する
- 人が確認すべき条件を設計する
- 前提や例外を拾う
- 判断と変更の根拠を残す

この深さを、各コースの中に載せます。

# まとめ

再現性のある志望理由ESは、次の型で作ります。

```text
① 実現したい状態
　自分が作りたい価値を最初に置く。

② 原体験からの問題意識
　過去の詳細ではなく、なぜその価値観を持ったかを書く。

③ 現在との差分
　ここまでは経験したが、実務条件ではまだ経験がないと示す。

④ Why御社
　自分の価値観
　× 企業の仕事の性質
　× 担う責任
　× 発生する判断
　× 自分の強み。

⑤ Whyそのコース
　コース対象
　× 工程
　× 制約
　× 発生する判断
　× 自分に足りない経験。

⑥ 学び・貢献
　何を学びたいかではなく、どんな判断軸を身につけ、どんな強みで貢献するかを書く。
```

最終方針は以下です。

```text
構造はNTTデータ型。
深さはNEC型。
素材は職種別。
締めは学びだけでなく貢献。
```

この型を使えば、志望理由は毎回ゼロから悩むものではなく、企業・コースごとに設計できるものになります。
