# NTTデータ 技術変化・開発方法

## 位置づけ

このノートは、NTTデータが公式に発信している技術変化、開発方法、品質保証、現場の役割変化を整理する。

AIだけに限定せず、開発プロセス、品質・説明責任、データ・インフラ、コンサルティングとの接続も扱う。

## 確認できた技術発信の要点

- GitHubとの連携により、生成AIをシステム開発に適用し、開発プロセスの効率化と品質向上を進めている。
- AI-Native開発では、AIを補助ツールとして使うだけでなく、AIが直接扱える形に開発環境・成果物・ルールを再構成することを重視している。
- 商用システム開発では、機能性だけでなく、品質、透明性、アカウンタビリティを満たす必要があると整理している。
- Technology Foresight 2026では、自律的エージェント、信頼できる知能、AI-readyなインフラ、半導体、エネルギー制約など、AI時代の技術基盤全体の変化を示している。

## AI-Native開発

### 定義

NTTデータのAI-Native開発レポートでは、AI-Native開発を、AIを開発の主体に据え、AIが最大限の能力を発揮できるよう開発環境そのものを最適化するアプローチとして説明している。

要点は次の3つ。

- 開発の主体を、人間中心からAIエージェント中心の協働へ移す。
- 要件、設計、手順、ルールを、AIが直接扱えるテキスト、API、CLI中心に再構成する。
- 人間の役割を、実装そのものから、方向づけ、監督、説明責任へ移す。

### 商用システムで重視する4つの責務

| 責務 | 内容 | 現場での意味 |
| --- | --- | --- |
| 機能性 | システムが定義された機能を提供すること | AIが動くものを作る力は高まるが、それだけでは不十分。 |
| 品質 | システムが期待通りに動作すること | 要件の曖昧さ排除、品質基準、テスト、レビューが重要。 |
| 透明性 | 開発プロセスが証跡として記録され、第三者が検証可能であること | AIが参照した情報、判断、生成過程、承認記録を残す必要がある。 |
| アカウンタビリティ | 意思決定を説明・正当化できること | AIの出力でも、最終的な説明責任は人間・組織に残る。 |

### スリーラインモデル

AI-Native開発のレポートでは、商用システム開発にスリーラインモデルを適用している。

| 役割 | 主な責務 |
| --- | --- |
| 第一ライン: 開発チーム | 開発実務、機能性、プロセス内での品質作り込み |
| 第二ライン: PMO・品質保証 | 開発標準、品質基準、モニタリング、品質ゲート |
| 第三ライン: 内部監査 | 統制プロセスの有効性を独立した立場で検証 |
| ガバナンス体 | ステークホルダーへの説明責任 |

この整理は、AI活用を単なる効率化ではなく、価値創出とガバナンスの両立として捉えている点が重要である。

### 成熟度モデル

| 段階 | AIが担う範囲 | 人間が担う範囲 | 移行の鍵 |
| --- | --- | --- | --- |
| AI-Assisted | 補助的なコード補完・支援 | 機能性、品質、透明性、説明責任の大半 | 既存開発へのAI導入 |
| Level 1: AI-Generated | 開発実務を担い、動くものを生成 | 品質の作り込み、レビュー、判断 | AI-readableな文脈、タスク分解 |
| Level 2: AI-Verified | 品質監督の一部も担う | プロセス管理、透明性確保 | エージェント型監督、品質ゲート |
| Level 3: AI-Explainable | 透明性の一部も担う | 事後監査、説明責任 | 来歴追跡、検証可能性、社会的受容 |

Level 3は直近の導入目標というより、技術的・制度的条件が整った先の長期的方向性として説明されている。

## GitHub Copilot・生成AI開発支援

### 公式発表で確認できること

- 2024年10月、GitHubとのビジネス連携により、生成AIをシステム開発へ適用すると発表。
- 2024年時点で、NTTデータグループ全体の国内利用は約2,000ユーザー・70以上のプロジェクト。
- 2025年度中に国内でGitHub Copilotの5,000ユーザー利用を目指すと発表。
- システムインテグレーション業務や自社サービス開発にGitHub CopilotやAzure OpenAI Serviceを活用し、開発生産性16.5%向上を掲げる。
- 2024年12月のDATA INSIGHT記事では、100以上のプロジェクト、2,000以上のユーザーでGitHub Copilotを採用していると説明。
- 同記事では、2027年度までにソフトウェア開発工程全体の生産性50%向上を目標としている。

### 現場への示唆

- 生成AI活用は、コーディング補助に留まらず、設計工程、テスト工程、エラー解析、品質向上へ広がっている。
- セキュアな利用環境、ガイドライン、リスク低減、AIガバナンスとセットで進めている。
- 生成AIを使えるだけではなく、プロンプト設計、出力検証、品質基準、ノウハウ共有が重要になる。

## AI時代の業務・基盤設計

### 業界特化型AIエージェント

OpenAIとの提携では、金融、製造、流通、ヘルスケア、公共など、業界特有の課題を理解したAIエージェントの開発・提供を掲げている。

これは、単にAIモデルを提供するのではなく、業界知識、業務プロセス、既存システム、データを理解した上で、業務変革に結びつける方向性として確認できる。

### 共同利用型AI基盤

金融機関向け共同利用型AI基盤では、次の4つの設計思想が示されている。

- 金融機関に求められる信頼性を担保するAIガバナンス。
- 既存資産を最大限活用するデータ統合。
- 特定のAIモデルやクラウド事業者に依存しないマルチベンダー設計。
- 業界横断で知見を共有する共創基盤。

この発信から、今後の現場では、AIそのものだけでなく、ガバナンス、データ統合、既存システム接続、運用、共創設計が重要になることが確認できる。

### AI-readyなインフラ

Technology Foresight 2026では、知能システムの高度化と計算需要の急拡大により、物理サーバー、ネットワーク、データセンターが再び戦略資産として重要になると説明している。

AI活用の現場では、アプリケーション、モデル、データだけでなく、計算資源、データ所在地、クラウド依存、主権性、透明性、エネルギー制約も考慮する必要がある。

これは公式発信からの整理であり、選考用の自己接続は `01_選考対策/NTTデータ/企業分析.md` に置く。

| 力 | 根拠となる会社発信 | 現場での意味 |
| --- | --- | --- |
| 要件・業務を構造化する力 | AI-Native開発では、AIが扱えるよう要件・設計・手順・ルールを再構成する。 | 曖昧な業務要望をAIや開発チームが扱える粒度に分解する。 |
| 品質と説明責任を担保する力 | 商用システムには品質、透明性、アカウンタビリティが必要。 | AIの出力を鵜呑みにせず、根拠、証跡、テスト、承認を設計する。 |
| 変化対応力 | 人材戦略では、変化に対応しデジタル業界をリードできる高度専門人材を育成。 | 新技術を学び、既存プロセスを改善する。 |
| 業界・業務理解 | 業界特化型AIエージェント、金融向け共同AI基盤を展開。 | 技術だけでなく、金融、公共、製造など顧客業務の制約を理解する。 |
| 共創力 | 共同利用型AI基盤、コンサルティング、公式採用の共創力。 | 顧客、社内外専門家、パートナー、AIエージェントと協働する。 |

- 2027年度までの生産性50%向上目標に対する最新の進捗。
